# ADR 0005 — Reproducible, non-person/machine-dependent setup

- **Status:** accepted
- **Date:** 2026-06-09
- **Supersedes:** —
- **Superseded by:** —

## Context

The platform must be operable by any contributor from their own machine and accounts and
produce the **same** result — no step may depend on one person's laptop, home directory,
shell history, locally-cached artifact, or ad-hoc command. Today the dev cluster bring-up is
automated via `make` targets (`make bringup`), but two classes of person/machine coupling are
easy to introduce by accident:

1. **Machine-specific values committed to the repo** — hardcoded absolute home paths
   (`/home/<user>/…`), a contributor's username/email, ephemeral node IPs, or a specific SSH
   key path. These work on the author's machine and silently break (or mislead) everyone else.
2. **Per-operator artifacts instead of shared ones** — the current registry-less image
   delivery builds the image on the operator's laptop and imports it into the cluster nodes
   over that operator's SSH access. On a shared cluster only the provisioner can update the
   image, and there is no shared image artifact a colleague (or CI) can reuse.

## Decision

**Everything a contributor needs is reproducible from this repo with documented commands, and
nothing in tracked files is specific to one person or machine.**

- Tracked files reference `$HOME` / `~` and tool-discovered values (e.g. `kubectl get node …`),
  never literal `/home/<user>` paths, usernames, or ephemeral IPs. Enforced by the quality gate
  (`/home/[a-z]` is a forbidden pattern outside the doc allow-list; see `docs/invariants.md`).
- Per-person **secrets and keys** are supplied through standardized, gitignored locations the
  tooling creates or prompts for — the Hetzner token in `.local/hcloud.env` (via `make preflight`)
  and the node SSH key at `~/.ssh/id_ed25519` (auto-generated by `make preflight` if absent, and
  the single path referenced by both the cluster config and the image-import target so they can
  never drift). The *mechanism* is identical for everyone; only the secret values differ.
- Bring-up, image build, and image delivery are `make` targets (`make bringup`), not memorized
  commands — see ADR 0003 (self-documenting automation) and the operator-automation principle.
- **Shared artifacts over per-machine ones.** The registry-less SSH import is an accepted
  interim only; a real container registry (image built/pushed once — ideally by CI — and pulled
  by any cluster) is the target state, removing the last per-operator coupling. Tracked as a
  Phase 2/4 follow-up.

## Consequences

- A colleague reproduces the platform with: `make preflight` (one-time; supplies token + key)
  → `make bringup` → `make app-forward`. Identical outcome on any machine/account.
- The gate fails any PR that commits a hardcoded home path, catching the most common regression
  mechanically rather than by review.
- Until the shared registry lands, updating the image on a shared cluster still depends on an
  operator with SSH access to the nodes; this is the known exception this ADR commits to closing.
